# Decisions

1. Hermes `0.21.3` was inspected as a behavior reference only. Its terminal tool has reusable principles, including session-aware CWD, bounded terminal output, foreground/background separation, and a process registry, but its product integrations were not copied.
2. NyxStrike `1.9.0` was inspected as a FastMCP bridge to its server. Its dashboard/API and hardcoded catalog are excluded. Fenrys exposes only a generic optional MCP provider contract.
3. The LangGraph milestone uses `langgraph 0.6.11` APIs: `StateGraph`, `START`, `END`, `InMemorySaver`, and optional persistent `SqliteSaver`. The graph has `reason -> act -> reason` control flow and list reducers for accumulated state.
4. The LLM is an explicit provider-neutral `Reasoner` protocol. `JSONHTTPReasoner` reads endpoint/key settings from environment only; no provider SDK or credential is embedded in graph logic.
5. Runtime isolation is present from the first slice: dedicated session workspace, bounded memory/CPU/output, timeout, and process group termination. Network policy is represented by `RuntimeConfig.target_networks`; no hidden firewall is imposed.
6. Archive extraction was validated before extraction. Both archives were checked for zip-slip paths and capped at 512 MiB uncompressed total.
7. MCP is implemented as a generic `ToolProvider` boundary in `fenrys_cai.mcp`. Provider-specific servers are external processes/services; Fenrys core knows only MCP tools, schemas, results, and normalized errors. MCP `1.30.0` APIs are used for stdio and Streamable HTTP transports.
8. NyxStrike is an external MCP provider and is not a Fenrys core dependency. Live validation used a running NyxStrike API server (`1.9.0`) and its `nyxstrike_mcp.py` bridge via stdio. Fenrys discovered `classify_task` and `run_tool` dynamically and invoked `hashid` safely through the generic `MCPProvider`. No NyxStrike source was copied or imported into Fenrys core.
9. Specialists are reasoning components sharing the Fenrys runtime, Tool Registry, and CyberState rather than independent agent runtimes. Eleven domains exist (`recon` through `verification`), each backed by a Fenrys-native prompt file and an injected decision builder. Routing is signal-based, not tool-catalog-based. Delegation is depth-limited and returns through LangGraph rather than spawning subprocesses.
10. Specialist reasoning uses the same provider-neutral LLM interface as the primary reasoning loop. `LLMSpecialistDecisionBuilder` constructs bounded messages, calls the configured endpoint via `httpx`, and validates the response strictly. No provider SDK is imported into specialist code. Real-provider validation succeeded with an Anthropic-compatible endpoint returning a structured `tool` decision.
11. Specialist outputs are schema-validated before execution. Malformed JSON, missing decisions, invalid tool names, invalid domains, and non-dict arguments raise `SpecialistLLMError` and become structured `stop` decisions. Malformed model output never reaches `ToolRegistry` or executes a tool.
12. Primary reasoning and specialist reasoning use the same provider-neutral `LLMProvider` abstraction in `fenrys_cai/llm/provider.py`. `JSONHTTPReasoner` and `DemonstrationReasoner` are removed from the production path. `PrimaryReasoner` uses `prompts/primary.md` and validates decisions strictly. Real-provider validation succeeded for primary reasoning with an Anthropic-compatible endpoint.
13. Hypothesis status is state-machine controlled and cannot be arbitrarily mutated by LLM output. All transitions, evidence attachment, verification creation, conclusions, and supersession pass through `HypothesisEngine`; invalid transitions return typed `LifecycleError` values.
14. Verification requires evidence; successful tool execution alone is not proof. Confirmation requires an expected observation, an actual observation, and at least one supporting evidence reference. Tool status, exit code, HTTP status, and model confidence remain metadata only.
15. `continue` is a valid transition back to `REASON`, bounded by machine-enforced iteration, tool-call, runtime, and anti-loop controls configured through `LoopConfig`.
16. Duplicate-action prevention uses normalized attempt identity plus meaningful context changes, not raw command-string matching. Parameters, strategy, target, hypothesis, and progress tokens determine whether a retry is materially different.
17. Verification completion requires explicit evidence, a deterministic matcher (or future structured LLM verifier), and a valid `HypothesisEngine` lifecycle transition. No result status implicitly confirms a claim.
18. Large outputs are stored as bounded artifact references rather than unlimited raw state. Local artifact files are content-hashed, path-isolated, size-capped, and range-readable.
19. Secret redaction is centralized before result serialization and persistence. Credentials are removed from nested mappings, environment inheritance, errors, prompts/state exports, and artifact metadata.
20. Background processes are reattached only when Fenrys can establish process identity through its runtime marker. PID existence alone is insufficient; uncertain identities are marked disappeared and never terminated.
21. Deterministic verification is preferred; `LLMVerifier` is a strict provider-neutral fallback for inconclusive semantic evidence and cannot mutate hypothesis state.
22. `max_repeated_attempts` means the number of unjustified duplicate executions allowed: zero blocks the first duplicate, one permits one duplicate, and so on; iteration/tool/runtime limits still prevent unbounded repetition.
23. End-to-end validation uses a deterministic local CTF harness, not production shortcuts. Fake LLM responses select normal graph decisions; tools, artifacts, hypotheses, anti-loop, verification, and checkpoints are real production components.
24. A bounded anti-loop reconsideration option records and blocks a duplicate but can route back to `REASON` once so an engagement remains solvable through a changed strategy. The default remains zero for fail-closed behavior.
25. Real-LLM E2E validation is reported separately from deterministic acceptance. The Sep 2026 run stopped safely after a provider timeout and did not fabricate a verified flag; deterministic E2E remains the reproducible acceptance gate.
26. Core local ToolSpecs use strict JSON Schema matching actual LocalProvider arguments. This is the production contract supplied to all providers, not a vendor-specific schema.
27. Transient provider failures may retry once by default through checkpointed graph state. Authentication failures and malformed/invalid model output are non-retryable because retrying them cannot safely improve the same request.
28. The Milestone 11 real-provider E2E showed improved workspace-relative argument use and file discovery but still failed before hypothesis/verification due to malformed model output. This remains an observed provider reliability limitation, not a verified completion.
29. Custom providers are configured through `LLMProvider` rather than dedicated clients. `FENRYS_LLM_PROTOCOL` explicitly selects `openai` or `anthropic`, preventing unrelated inherited provider environment from changing the custom endpoint protocol.
30. Specialist LLM decisions now delegate transport, authentication, response parsing, and normalized errors to the same `LLMProvider` as primary reasoning; no legacy specialist HTTP path remains.
31. TUI `prompt.submit` previously called `run(CyberState(session, message))` for every message. Because unreduced LangGraph state keys overwrite checkpoints, that reset the objective, phase, completion state, counters, clock, provider state, and specialist depth despite retaining reducer-backed collections. `continue_session` now supplies a minimal per-turn delta to existing threads and a full initial state only for unseen sessions.
32. Per-turn execution limits are reset deliberately while engagement knowledge is retained. The delta adds a tagged `user_directive:` history item, clears stale routing/completion state, and resets iteration/tool/runtime/provider/anti-loop/specialist bookkeeping; it does not provide objective, phase, or cumulative fields. Installed LangGraph behavior was verified by regression tests: omitted state keys remain checkpointed and merged attempts still block a duplicate across turns.
33. Terminal responsiveness uses LangGraph update streaming over the existing stdio JSON-lines gateway. No HTTP, browser, WebSocket, dependency, or checkpoint schema change was introduced. The gateway emits node-specific live events and preserves its existing final `turn.complete` payload and request result contract.
